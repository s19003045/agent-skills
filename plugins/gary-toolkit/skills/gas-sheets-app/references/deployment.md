# 部署流程

這份是給**不會寫程式的人**照著做的版本。可以直接改寫成交付給使用者的教學文件。

全程約 40 分鐘，不需付費，不需 Google Workspace（個人 Gmail 即可）。

## 順序為什麼是這樣排的

**先在本機測到會動，再正式上線。** 這樣萬一哪裡錯了，會在第 8 步就發現，
而不是全部弄完才發現不能用 —— 「已上線但不能用」是最難排查的狀態。

部署過程會產生 **4 個值**，後面步驟會用到。建議在教學裡提供一個「值收集區」讓使用者貼著：

| 值 | 來自 | 長什麼樣 |
|---|---|---|
| 試算表 ID | 步驟 1 | `1AbCdEf...` |
| 資料夾 ID | 步驟 2 | `1XyZ...` |
| 後端網址 | 步驟 4 | `https://script.google.com/macros/s/.../exec` |
| 用戶端 ID | 步驟 5 | `...apps.googleusercontent.com` |

---

## 步驟 1：建立試算表

`sheets.google.com` → 空白試算表 → 命名。
從網址列複製 `/d/` 和 `/edit` 中間那一段，就是**試算表 ID**。

```
https://docs.google.com/spreadsheets/d/【這一段】/edit
```

## 步驟 2：建立檔案資料夾（若需要上傳功能）

`drive.google.com` → 新增 → 新增資料夾 → **連點兩下進入該資料夾**（不進去網址不會變）。
網址列 `folders/` 後面那一段就是**資料夾 ID**。

檔案會存在使用者自己的 Drive（免費帳號 15GB），不需要 Service Account。

## 步驟 3：安裝後端程式

試算表選單「擴充功能」→「Apps Script」。

**用 `scripts/build-bundle.mjs` 把後端合併成單一檔案再交給使用者。**
逐一貼十幾個檔案對非工程師負擔太重，而且容易漏。

1. `Code.gs` 全選刪除 → 貼上合併後的檔案 → 存檔
2. 左側齒輪「專案設定」→ 勾選「在編輯器中顯示 appsscript.json」
3. 回編輯器點 `appsscript.json` → 全選刪除 → 貼上你的 manifest → 存檔

**第 2、3 步不能跳過**。manifest 負責時區與 OAuth 權限清單，
少了它時間會錯十幾個小時、權限會不足（見 platform-traps #3、#4）。

## 步驟 4：部署成網路服務

「部署」→「新增部署作業」→ 齒輪選「網頁應用程式」：

| 欄位 | 必須選 |
|---|---|
| 執行身分 | **我（你的帳號）** |
| 具有存取權的使用者 | **所有人** |

**這裡最常選錯。** 要主動解釋：「所有人」不代表資料公開，它只是允許任何人敲門，
每個請求仍必須附有效的 Google 憑證且帳號要在名冊裡。選「僅限我自己」會把所有使用者擋在門外。

第一次部署會跳出授權請求，出現「**Google 尚未驗證這個應用程式**」。
**這個畫面一定要事先說明**，否則多數人會停在那裡不敢按：
點「進階」→「前往 ...（不安全）」→「允許」。
它是自己安裝在自己帳號下、只有自己使用的程式，沒有送 Google 商業審查所以顯示這個警告。

完成後複製 `/exec` 結尾的網址，就是**後端網址**。

**立刻驗證**：把該網址貼到瀏覽器打開，應該看到 `{"success":true,...,"status":"ok",...}`。
這一步能立即分辨「後端沒上線」和「前端設定錯」，值得放進教學。

## 步驟 5：申請 Google 登入

`console.cloud.google.com` → 新增專案 → 切換到該專案。

**OAuth 同意畫面**：使用者類型選「外部」，填應用程式名稱與聯絡信箱，
範圍那頁不用動。**測試使用者**那頁要把所有會用到系統的 Gmail 都加進去。

> 沒加進測試使用者的人無法登入。之後每新增一個使用者都要回來補，
> 這是上線後最常遇到的問題，一定要寫進操作手冊。

**憑證** → 建立憑證 → OAuth 用戶端 ID → 網頁應用程式：

「已授權的 JavaScript 來源」**同時加入這兩個**（Google 視為不同來源）：
```
http://localhost:5173
http://127.0.0.1:5173
```
「已授權的重新導向 URI」不用填（ID Token 流程不需要）。

複製**用戶端 ID**。

## 步驟 6：把值填回系統

**兩個地方**：

Apps Script → 專案設定 → 指令碼屬性，新增（名稱大小寫要完全一致）：

| 屬性 | 值 |
|---|---|
| `CLIENT_ID` | 步驟 5 的用戶端 ID |
| `DRIVE_FOLDER_ID` | 步驟 2 的資料夾 ID |
| `SPREADSHEET_ID` | 步驟 1 的試算表 ID |

前端設定檔 `web/js/config.js`，把兩個空字串填入對應的值。
提醒使用者：**單引號和行尾分號都要留著**，刪掉的話網頁會整個打不開。

## 步驟 7：初始化與自我檢查

Apps Script 上方函式下拉選單選 `setupSpreadsheet` → 執行 → 回試算表確認工作表都建好了。

再執行 `verifySetup` → 看「執行記錄」，每一項都要是 `[通過]`：

```
=== 全部通過 ===
[通過] 時區設定 — Asia/Taipei
[通過] 指令碼屬性 CLIENT_ID / DRIVE_FOLDER_ID — ...
[通過] 試算表可存取 — ...
[通過] 工作表結構 __RBAC_Roles — 1 筆資料
[通過] Drive 資料夾可寫入 — ...
[通過] 可取得帳號 email（需 userinfo.email 權限）— you@gmail.com
[通過] 名冊中至少有一位 ACTIVE 管理者 — you@gmail.com
[通過] 對外網路請求可用 — HTTP 400
```

最後一項回傳 400 是**正常的** —— 那是故意送一個無效憑證去測連線通不通。
這種反直覺的輸出要在教學裡先說明，否則使用者會以為失敗了。

**有任何 `[失敗]` 就先不要往下走**，訊息會直接指出哪裡不對。

## 步驟 8：本機測試

```bash
npm run serve      # 用 scripts/serve.mjs，不要用 python3 -m http.server
```

**一定要手動輸入 `http://localhost:5173`。** 不要點終端機印出的連結
—— 那可能是 `http://0.0.0.0:5173`，Google 一律拒絕（見 platform-traps #7）。

登入成功、看到正確的角色和畫面，才算通過。

## 步驟 9：填名冊與初始資料

直接在試算表編輯。**名冊維護刻意不做成 API** —— 管理者本來就有試算表的完整權限，
做一套 CRUD 介面是多餘的工作量，還多一個要維護的授權面。

每加一個人，記得回步驟 5 把他的 email 加進「測試使用者」。

## 步驟 10：正式上線

最省事的靜態託管是 **Netlify Drop**（`app.netlify.com/drop`）——
把 `web` 資料夾整個拖進去就好，免費，會請使用者註冊帳號。
GitHub Pages 和 Cloudflare Pages 也可以，但對非工程師門檻較高。

**上線後還有最後一步**：回 Google Cloud → 憑證 → 你的用戶端 ID →
「已授權的 JavaScript 來源」加入正式網址（**結尾不要有斜線**）。
不做這步學生會全部登入失敗。變更最多要 5 分鐘生效。

## 建議一併交付的東西

- **自動備份**：執行一次 `installTriggers()` 建立每週快照。
  Google Sheet 沒有交易機制，誤刪只能靠快照還原。
- **操作手冊**：日常維護怎麼做（新增使用者、停用、匯出資料、常見狀況）。
- **疑難排解表**：見 `troubleshooting.md`。
- **「改了程式碼要建新版本」的提醒**：這是最常見的除錯陷阱（platform-traps #11）。
