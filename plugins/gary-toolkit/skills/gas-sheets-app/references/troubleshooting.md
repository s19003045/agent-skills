# 疑難排解對照表

依「使用者看到什麼」查詢。每一則都是實際遇過的。

## 登入相關

### 「已封鎖存取權：授權錯誤」`400: invalid_request`

**先看網址列。** 如果是 `http://0.0.0.0:PORT`，這就是原因 ——
`0.0.0.0` 不是主機名稱，Google OAuth 一律拒絕，也填不進「已授權的 JavaScript 來源」。
改用 `http://localhost:PORT`。

不是的話，逐字比對「目前網址來源」與 Google Cloud →憑證→你的用戶端 ID→
「已授權的 JavaScript 來源」清單。常見的不一致：

- 結尾多了斜線
- 通訊埠不同
- `localhost` 與 `127.0.0.1` 混用（Google 視為兩個來源）
- `http` 與 `https` 混用

剛改完設定最多要等 5 分鐘生效。

> 登入頁應該內建一個「診斷資訊」面板顯示這三個值，否則使用者無從比對。

### 登入按鈕沒反應，或 `origin_mismatch`

同上，來源沒登記。注意登入按鈕是由 Google 的 SDK 繪製的，
若 SDK 載入失敗按鈕根本不會出現 —— 檢查主控台有沒有網路錯誤。

### 「此帳號不在名冊中」

1. **看訊息括號裡的 email** —— 那是 Google 實際回報的地址。
   公司／學校帳號常有別名，管理者填的可能是別名而 Google 回報主要地址。
2. 確認名冊那一列沒有多餘空白（系統會自動轉小寫並 trim，但值得檢查）。
3. 確認該 email 已加入 OAuth 同意畫面的「測試使用者」。

如果剛加進去就試，而系統**沒有**實作「查無此人時重讀快取」，要等 TTL 過期（見 platform-traps #8）。

### 「Google 尚未驗證這個應用程式」

正常現象，不是錯誤。點「進階」→「前往 ...（不安全）」→「允許」。
自己安裝在自己帳號下、只有自己使用的程式沒有經過商業應用程式審查，所以顯示這個警告。

### 使用者填到一半突然要重新登入

ID Token 只有 1 小時。前端要實作靜默續發（platform-traps #10）。

## 執行 / 部署相關

### `Specified permissions are not sufficient to call ...`

`appsscript.json` 的 `oauthScopes` 少了那個 API 需要的權限。
明確宣告清單會關閉自動偵測，清單必須涵蓋每一個用到的 API（platform-traps #4）。

改完 manifest 後重新執行會**再次要求授權**（權限清單變了），這是正常的。

**順便檢查**：這個例外會中斷整個函式，它後面的步驟可能被無聲跳過。
初始化函式尤其要確認後續步驟有沒有真的執行（例如範本資料是不是空的）。

### 所有 API 呼叫都失敗，主控台顯示 CORS 錯誤

前端的 `Content-Type` 必須是 `text/plain;charset=utf-8`。
用 `application/json` 會觸發 preflight，而 Apps Script 不回應 preflight（platform-traps #1）。

### 改了程式碼但行為完全沒變

Web App 網址綁定的是**部署版本**，不是最新程式碼。
「部署」→「管理部署作業」→ 鉛筆圖示 → 版本選**新版本** → 部署。
這樣網址不變。按「新增部署作業」會產生全新網址，前端設定要跟著改。

### 時間判斷完全不對

確認 `appsscript.json` 的 `timeZone`。`verifySetup()` 應該要檢查這一項。
改完 manifest 記得重新部署。

### 網頁一片空白

通常是設定檔的語法被改壞（刪掉了引號或分號）。
按 F12 看主控台有沒有紅字。這也是為什麼設定值最好集中在一個檔案的兩三行。

## 資料相關

### 存進去的值變了樣

- `'0123'` 變成 `123` → 試算表自動轉型
- 開頭是 `=` 的內容變成公式 → 同上，而且有資料外洩風險

三項對策都要做：純文字格式、寫入跳脫、讀取正規化（platform-traps #2）。

### 兩個人同時操作，其中一個人的資料不見了

`LockService` 沒包住完整的「讀→檢查→寫」，或寫入時用了鎖外讀到的舊值（platform-traps #5）。

### 檔案類型判斷對某些檔案永遠失敗

`Utilities.base64Decode` 回傳有號位元組，比對前要 `& 0xFF`（platform-traps #9）。

### 加了一個欄位之後系統崩潰

有地方寫死了欄位位置。一律用標頭動態對照，並在啟動時驗證必要欄位是否齊全。

### 資料被誤刪

如果有裝週期備份觸發器，Drive 裡會有快照。
沒有的話現在就裝（`installTriggers()`）—— Google Sheet 沒有交易機制，這是唯一的救援手段。

## 效能相關

### 「系統忙碌中」

`LockService` 取鎖失敗。Apps Script 同時執行上限 30。
前端應該做指數退避重試；若整批使用者都卡住，請他們分批操作。

### 每個動作都要等好幾秒

這是 Apps Script 的固有成本（1～3 秒／次）。可以做的：

- **減少往返次數**：一個 API 回傳整頁所需的資料，而不是分成三個小 API
- **快取讀多寫少的表**（但要處理 platform-traps #8）
- **UI 要有明確的忙碌狀態**，否則使用者會重複點擊

如果這樣還是不夠快，代表選錯架構了，該換 Serverless Functions 或一般後端。

### 上傳大檔案失敗

Base64 管線的實務上限約 5 MB（編碼會膨脹約 33%，加上 Apps Script 的承載量與執行時間限制）。
需要更大的檔案要改用 Drive resumable upload：由 Apps Script 建立上傳 session、
回傳 session URL，讓瀏覽器直接 PUT 到 Google，繞過 Apps Script 的承載限制。
這條路可行但要實測驗證瀏覽器端的 CORS 行為。
