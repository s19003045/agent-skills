# 用 Google 試算表 + Apps Script 做無伺服器應用

這份 skill 來自一個真實專案的完整開發與部署過程。裡面的每一個「陷阱」都是實際踩過、
花掉數小時才查出來的，不是從文件抄來的注意事項。

## 這套架構適合什麼

- 使用者人數在 **100 人以內**，每人每天操作次數不多
- 資料量在**數千列以內**
- 需要**不同角色看到不同資料**（管理者／編輯者／一般使用者）
- 希望**零主機成本、零維運**，而且不需要 Google Workspace（個人 Gmail 就能做）
- 資料本來就適合用試算表管理，管理者習慣直接開試算表編輯

## 什麼時候不要用

先講清楚，免得做到一半才發現走錯路：

| 情況 | 為什麼不行 | 改用什麼 |
|---|---|---|
| 超過 150 人同時操作 | Apps Script 同時執行上限 30，會大量排隊 | 一般後端 + 資料庫 |
| 需要即時互動（聊天、協作編輯） | 每次呼叫要 1～3 秒 | WebSocket + 後端 |
| 資料量上萬列且需要複雜查詢 | 每次都要讀整張表 | 真正的資料庫 |
| 檔案上傳超過 5 MB | Base64 管線的實務上限 | 物件儲存 + 簽章網址 |
| 使用者在有日光節約時間的地區 | 固定時區偏移會一年錯兩次 | 見 `references/platform-traps.md` 的時區章節 |

**在動手前先把這張表跟使用者確認過。** 這比做到一半再改架構便宜太多。

## 第一個、也是最重要的決策

使用者常會說「我要做純前端、不要後端」。這個想法是對的，但**字面上的「只有前端」做不到**，
必須先把這件事講清楚，否則會做出一個完全沒有安全性的系統。

原因是 **Google 的權限是「檔案級」的，不是「列級」或「欄級」**：

如果讓瀏覽器直接帶使用者的權限去打 Sheets API，那每個使用者都必須擁有整份試算表的編輯權。
於是他打開 DevTools 或直接用 curl 就能：改自己的成績、把自己的角色改成管理員、
讀走所有人的個資、刪掉整張表。前端寫的任何檢查都只是「建議」，不是「強制」。

**Apps Script Web App 是這個架構下的最小信任邊界**：

```
┌─ 不可信區（使用者完全控制）──────────┐
│  瀏覽器 SPA（靜態託管）               │
│  ・Google 登入取得 ID Token           │
│  ・對試算表與 Drive 沒有任何權限       │
└──────────────┬────────────────────────┘
               │ HTTPS POST（text/plain + JSON 字串）
     ══════════╪═══════ 信任邊界 ═══════
               ▼
┌─ 可信區（Apps Script，以擁有者身分執行）┐
│  驗證 ID Token → 查名冊決定角色          │
│  → LockService 序列化 → 讀寫             │
│  ├─▶ Google 試算表                      │
│  └─▶ Google Drive（檔案）               │
└─────────────────────────────────────────┘
```

對使用者來說「沒有伺服器要租、要部署、要維護」這件事仍然成立 —— Apps Script 跑在 Google 的機器上，
不用錢。但它**是**伺服器端程式碼，權限判斷全部發生在使用者碰不到的地方。

關鍵部署設定：**執行身分＝我（擁有者）**、**存取權＝任何人**。
「任何人」只代表任何人都能敲門，每個請求仍必須附上有效的 Google ID Token 且該帳號要在名冊裡。
選「僅限我自己」會把所有使用者擋在門外，而且錯誤訊息不會說原因。

完整的架構取捨與替代方案（含為什麼不用 Service Account）見 `references/architecture.md`。

## 工作流程

### 階段 0：確認範圍（不要跳過）

跟使用者確認：**人數上限、資料量、角色有哪幾種、要不要傳檔案、使用者所在時區**。
對照上面的「什麼時候不要用」。時區特別重要，它決定時間處理能不能用簡單的固定偏移。

### 階段 1：先搭骨架，不要先寫功能

複製 `assets/gas-core/` 的檔案當起點。這些是實際跑過的程式碼，已經處理掉所有已知陷阱：

| 檔案 | 用途 | 要不要改 |
|---|---|---|
| `appsscript.json` | 時區與 OAuth 權限清單 | 改時區 |
| `00_config.js` | 工作表名稱、欄位、角色、限制 | **一定要改** |
| `01_errors.js` | AppError 與錯誤碼 | 不用改 |
| `02_util.js` | 型別正規化、標頭對照、時間、檔案 | 不用改 |
| `04_sheet.js` | 試算表讀寫（標頭動態對照） | 不用改 |
| `05_cache.js` | 快取與載入器 | 載入器要改 |
| `06_lock.js` | 併發控制 | 不用改 |
| `07_auth.js` | ID Token 驗證與 RBAC | 不用改 |
| `10_main.js` | doPost 路由與 action 註冊表 | **註冊表要改** |
| `20_actions_example.js` | 四個範例 action | **整個換掉** |
| `90_setup.js` | 一鍵建表 + 部署自我檢查 | 不用改 |
| `91_backup.js` | 每週自動備份 | 不用改 |

這套骨架**開箱即可跑**：原封不動複製過去就能執行 `setupSpreadsheet()`、
跑測試、完成部署。先確認整條路徑通了再開始改功能，比邊寫邊猜哪裡壞掉快得多。

**先讓 `setupSpreadsheet()` 和 `verifySetup()` 跑得起來再寫功能。** 這兩個函式會依 `SHEET_HEADERS` 把工作表建好、
驗證設定與權限。跳過這步直接寫功能，之後出錯會分不清是設定問題還是程式問題。

### 階段 2：純函式優先

Apps Script 的除錯體驗很差：沒有中斷點、看 log 要重新部署。因此把邏輯分成兩層：

- **純函式層**（`02_util.js`、你的領域規則）：不碰 `SpreadsheetApp` / `DriveApp`，可在本機秒級測試
- **轉接層**（action handler）：只負責讀寫與呼叫純函式

判斷規則、授權判定、統計計算、格式轉換 —— 全部放純函式層。這是這套架構下開發效率的關鍵。

### 階段 3：本機測試（不需部署、不消耗配額）

用 `assets/test-harness/` 的檔案，以 `vm.runInContext` 載入**實際要部署的那份原始碼**，
搭配 Google 服務的記憶體假實作，就能在本機完整跑過 `doPost` 的整條路徑。

裡面的 `smoke.test.js` 可以直接跑，涵蓋建表、自我檢查、身分驗證、RBAC、
資料讀寫、公式跳脫、欄位順序容錯。骨架搭好後第一件事就是讓它全過。

詳見 `references/testing.md`。這是整份 skill 裡最容易被低估、但價值最高的部分。

### 階段 4：前端

用 `assets/web-core/` 的 `api.js`、`auth.js`、`config.js`、`ui.js`。
`api.js` 已經處理好 CORS 寫法、token 過期自動續發、取鎖失敗的指數退避重試。

用 `scripts/serve.mjs` 當開發伺服器（**不要用 `python3 -m http.server`**，原因見陷阱 #7）。

### 階段 5：部署

執行 `scripts/build-bundle.mjs` 把後端合併成單一檔案，使用者只要複製貼上一次。
逐步流程見 `references/deployment.md`。

## 開發前必讀：Google 平台的陷阱

這八項每一項都會讓系統壞掉，而且錯誤訊息通常不會指向真正的原因。
`assets/gas-core/` 已經處理好全部，但你需要知道它們存在，才不會在改動時破壞掉。

**完整說明、重現方式與修法見 `references/platform-traps.md`。**

1. **CORS preflight** — Apps Script 不回應 OPTIONS 請求。前端用 `application/json` 會直接失敗，
   必須用 `Content-Type: text/plain` 送 JSON 字串。

2. **試算表自動轉型** — `'0123'` 存進去變成數字 `123`，開頭是 `=` 的字串變成公式。
   對策：全欄位設純文字格式 + 寫入跳脫 + 讀取正規化。

3. **時區預設不是你的時區** — 明確宣告 `oauthScopes` 時若沒設 `timeZone`，
   可能是美國西岸，時間判斷會差 15 小時。

4. **明確宣告 oauthScopes 會關閉自動偵測** — 少列任何一項，執行時就拋
   `Specified permissions are not sufficient`。`Session.getEffectiveUser` 需要 `userinfo.email`。

5. **併發覆寫** — 兩個請求同時「讀→改→寫」會互相蓋掉。
   `LockService` 必須包住**完整的讀取、檢查、寫入**，不是只包寫入那一行。

6. **檔案分享權限** — 用「知道連結的人可檢視」等於把資料公開到網際網路。
   改成預設私有、需要時才 `addViewer()` 精準授權。

7. **`0.0.0.0` 無法登入** — 開發伺服器印出的 `http://0.0.0.0:5173/` 在終端機是可點的連結，
   但 Google OAuth 一律拒絕它，而且它也填不進「已授權的 JavaScript 來源」。

8. **快取造成「查無此人」** — 名冊快取 TTL 內剛加入的人會被拒絕，訊息看起來像永久拒絕。
   對策：查無此人時略過快取重讀一次再決定。

還有兩個較小但一樣會咬人的：`Utilities.base64Decode` 回傳**有號位元組**（判斷檔頭要 `& 0xFF`）；
GIS 的 ID Token **只有 1 小時**有效，過期要能靜默續發。

## 錯誤訊息要寫得能自己排查

這套架構的除錯特別困難：Google 只回傳籠統訊息，使用者又通常不會看主控台。
所以錯誤訊息要主動把「該比對的東西」寫出來：

```javascript
// 不好：使用者只能反覆猜自己是不是拼錯
fail('NOT_ENROLLED', '此帳號不在名冊中');

// 好：直接寫出實際驗證到的 email
// 公司或學校帳號常有別名，Google 回報的主要地址未必等於名冊裡填的那個，
// 不寫出來根本無從察覺
fail('NOT_ENROLLED', '此帳號（' + email + '）不在名冊中，請確認管理者填入的是這個地址');
```

同樣的道理，登入頁應該有一個可展開的「診斷資訊」，顯示**目前網址來源、用戶端 ID、後端網址**。
Google 對登入失敗只回一句 `invalid_request`，從來不說是哪裡對不上；把要比對的值攤開，
使用者才有辦法自己查，你也才有辦法遠端協助。`assets/web-core/` 已經內建這個面板。

## 帶不會寫程式的人完成部署

這類專案的使用者常常是老師、行政、小店主 —— 他們能點按鈕、能複製貼上，但看不懂程式碼。
幾個實測有效的做法：

- **把後端合併成單一檔案。** 用 `scripts/build-bundle.mjs`，讓他們只要複製貼上一次，
  而不是把十幾個檔案逐一貼進編輯器。
- **每一步都寫「你應該會看到什麼」。** 他們無法從程式行為判斷對錯，只能比對畫面。
- **先在本機測到會動，再正式上線。** 避免出現「已上線但不能用」這種最難排查的中間狀態。
- **預先解釋會嚇到人的畫面。** 「Google 尚未驗證這個應用程式」這個警告一定會出現，
  沒有事先說明的話多數人會停在那裡不敢按。
- **提供「值收集區」。** 部署過程會產生 4 個 ID（試算表、資料夾、後端網址、用戶端 ID），
  後面步驟會用到；讓他們有地方貼著，不用回頭翻。

完整的逐步稿見 `references/deployment.md`，可以直接改成給使用者看的教學。

## 常見情境的處理方式

**使用者說「我不要 Apps Script，就純前端」** — 用上面「第一個決策」那段解釋為什麼做不到，
並提供替代方案：如果真的不需要權限控管（例如純唯讀的公開儀表板），
那把試算表發佈成 CSV 讓前端直接讀是可行的，這時確實不需要 Apps Script。
判斷標準是：**有沒有任何資料是「某些人不該看到」的**。

**使用者已經在做、卡在某個錯誤** — 直接查 `references/troubleshooting.md`，
那是一張「症狀 → 原因 → 修法」的對照表，涵蓋所有實際遇過的錯誤訊息。

**使用者想加功能** — 純函式層先寫規則和測試，再加 action 到註冊表。
記得註冊表的角色白名單就是授權的唯一定義處。
