# 架構決策

## 為什麼「純前端直連 Google API」不可行

這是使用者最常提出的想法，也是最需要花時間講清楚的一件事。

做法是前端跑 Google OAuth，拿使用者自己的 token 去打 Sheets API。
問題出在 **Google 的權限是「檔案級」的**，沒有列級或欄級權限。

使用者要能寫入自己那一列 → 就必須擁有整份試算表的編輯權 → 於是他能：

| 他能做的事 | 為什麼擋不住 |
|---|---|
| 把自己的角色改成管理員 | 他有寫入權，前端的角色判斷只是畫面裝飾 |
| 修改自己或別人的任何資料 | 同上 |
| 讀取全部人的個資 | 讀權限一併給了 |
| 刪掉整張工作表 | 有寫入權就有刪除權 |

**前端的任何檢查都只是「建議」，不是「強制」。** 強制必須發生在使用者控制不到的地方。

### 唯一適用純前端的情況

**沒有任何資料是「某些人不該看到」的。** 例如：

- 純唯讀的公開儀表板（把試算表發佈成 CSV，前端直接讀）
- 給自己看的個人工具
- 所有使用者本來就都有試算表編輯權的小團隊

這時確實不需要 Apps Script，可以真的只有前端。判斷標準就是上面那一句。

## 各種做法的取捨

| | 純前端直連 | **Apps Script** | 靜態前端 + Serverless Functions | 自架後端 |
|---|:---:|:---:|:---:|:---:|
| 權限可強制 | ❌ | ✅ | ✅ | ✅ |
| 要維運伺服器 | 否 | **否** | 否（但要管部署） | 是 |
| 費用 | 0 | **0** | 近乎 0 | 有 |
| 需要 Workspace | 否 | **否** | 視檔案方案而定 | 否 |
| 回應速度 | 快 | 慢（1～3 秒） | 快 | 快 |
| 檔案上傳上限 | 不限 | 5 MB | 不限 | 不限 |
| 同時操作人數 | 不限 | ~30 併發 | 高 | 高 |
| 開發／除錯體驗 | 好 | 差（clasp + 純函式可救） | 好 | 好 |

**選 Apps Script 的理由**：對 100 人以內的專案，它是投入產出比最高的 —— 零維運、零成本、
不需要 Workspace，而且**它天然是單執行緒且有官方鎖服務**，反而比自己寫佇列更不容易掉資料。
慢個 1～2 秒對這類使用情境不痛。

**改選 Serverless Functions 的時機**：超過 150 人、或需要更快的回應。
代價是要處理 Service Account 的 Drive 配額問題（見 platform-traps #12）。

## 信任邊界

```
┌─ 不可信區（使用者完全控制）──────────────┐
│  瀏覽器 SPA                                │
│  ・靜態託管（GitHub Pages / Netlify / …）  │
│  ・Google Identity Services 取得 ID Token  │
│  ・對試算表與 Drive 沒有任何權限            │
└──────────────┬─────────────────────────────┘
               │ HTTPS POST（text/plain + JSON 字串）
     ══════════╪═════════ 信任邊界 ═════════
               ▼
┌─ 可信區（Apps Script，以擁有者身分執行）───┐
│  1. 驗證 ID Token（aud / iss / email_verified）│
│  2. 查名冊決定角色 ← 唯一的授權來源          │
│  3. LockService 序列化寫入                   │
│  ├─▶ Google 試算表                          │
│  └─▶ Google Drive                           │
└──────────────────────────────────────────────┘
```

**核心不變式**：任何權限判斷只在信任邊界內發生。前端的角色判斷純屬 UI 呈現，不具安全意義。

### 部署設定（選錯會壞掉且訊息不會說原因）

| 設定 | 必須選 | 選錯的後果 |
|---|---|---|
| 執行身分 | **我（擁有者）** | 選「存取應用程式的使用者」→ 使用者需要試算表權限，整個模型崩潰 |
| 存取權 | **任何人** | 選「僅限我自己」→ 所有使用者被擋在門外 |

**「任何人」不等於資料公開。** 它只代表任何人都能對這個網址發出請求；
每個請求仍必須附上有效的 Google ID Token，且該帳號必須在名冊裡，否則一律拒絕。
這一點要主動跟使用者解釋，否則他們的直覺會選錯。

## 資料模型

因為沒有關聯式資料庫，設計時要接受這些限制：

**沒有交易。** 跨表的一致性要自己顧。實務做法：把需要一起成功的欄位放在同一列，
用 `LockService` 保護，並定期自動備份（`91_backup.js`）。

**沒有唯一索引。** 「同一個人同一週只能有一筆」這種約束要在鎖內自己檢查。

**永遠不要刪列。** 刪列會讓其他列的列號位移，也會讓歷史紀錄失去對照。
改用 `status` 欄位標記為停用。

**每次讀整張表。** 這決定了資料量上限。數千列還好，上萬列就該換架構。
讀多寫少的表（名冊、設定）用 `CacheService` 快取，但要注意 platform-traps #8。

**主鍵用 UUID，查找靠掃描。** `Utilities.getUuid()`。在這個資料量下線性掃描完全可接受，
而且比維護索引簡單得多。

**永遠不要寫死欄位位置。** 一律讀第一列建立「欄位名稱 → 索引」的對照表。
管理者哪天在試算表中間插一欄，系統不會崩。啟動時驗證必要欄位是否齊全，缺了就明確報錯。

## 效能預期

先跟使用者對齊期待，否則上線後會被質疑「怎麼這麼慢」：

- **每次 API 呼叫 1～3 秒**。Apps Script 的冷啟動很明顯，這是固有成本。
- **設計上要減少往返次數**。與其做三個小 API 各拿一點資料，不如做一個回傳整頁所需資料的 API。
  這跟一般 REST 的細粒度設計原則相反，但在這裡是對的。
- **UI 要有明確的忙碌狀態**。1～3 秒沒有回饋，使用者會重複點擊。
- **同時執行上限 30**。尖峰時要有退避重試，並在文件裡告訴管理者可以請使用者分批操作。
